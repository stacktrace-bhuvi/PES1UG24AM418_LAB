# Project Reflection: Static Analysis on Car Rental System

### Which issues were easiest and which were hardest to fix, and why?
The easiest issues to resolve were the mechanical quality and style warnings, such as removing the unused `json` import, renaming functions to snake_case, and adding missing docstrings across the module. Swapping weak cryptographic algorithms was similarly straightforward, as replacing SHA-1 with `hashlib.sha256` and switching from `random.randint` to `secrets.randbelow` only required changing one or two lines of code. In contrast, the hardest issues to fix involved architectural and functional redesigns, particularly eliminating the arbitrary code execution vector in `apply_promo` and securing temporary file creation in `write_receipt`. Refactoring `apply_promo` required abandoning `exec()` entirely in favor of an explicit percentage-based math model with input validation, while `write_receipt` demanded safe temporary file handling with atomic contexts and strict file permission masks.

### Did the tools give any false positives or findings that did not matter?
While almost all flagged issues identified genuine quality and security risks, a few findings felt somewhat pedantic or inconsequential for a small, self-contained educational script. For instance, Bandit flagged `admin_login` for hardcoding the default credentials `admin@rent`, which was clearly intended as basic placeholder data in a localized demonstration script rather than a leaked production secret. Additionally, Flake8's strict 79-character limit generated multiple warnings for perfectly readable function invocations and formatted print statements that Pylint had already deemed acceptable under its 100-character threshold. Bandit also warned about POSIX file permission modes on Windows when calling `os.chmod`, where Unix permission bits like `0o600` have limited effect compared to standard filesystem ACLs. Despite these slight nuances, addressing all of them ultimately produced a cleaner, more robust codebase.

### How would you use static analysis in a real workflow (e.g. pre-commit hooks, CI)?
In a professional engineering environment, I would embed static analysis at multiple stages of the development lifecycle to prevent flaws from reaching production. At the local developer level, I would configure Git pre-commit hooks using the `pre-commit` framework to automatically run fast linters like Flake8 and Bandit on staged files before code can even be committed. In our team's continuous integration (CI) pipeline, such as GitHub Actions, I would configure automated workflows to run Bandit, Flake8, and Pylint on every pull request, enforcing strict build gates that block merges if new security vulnerabilities arise or if the Pylint score drops below a set threshold like 9.5. This layered strategy establishes early feedback for engineers, prevents regressions, and eliminates manual nitpicking during code reviews.

### What did the tools miss that you only found by running and reading the program?
Although the tools were effective at detecting structural patterns like the SQL injection in `find_customer` and the unsafe `exec` call in `apply_promo`, they completely missed domain logic bugs that compromised the business workflow. For example, the linters never detected that `rent_car` accepted return dates earlier than start dates, which produced an absurd negative total cost for the customer. The tools also failed to catch that rented vehicles were never marked unavailable, permitting simultaneous double bookings of the Swift, and that `add_car` happily accepted a negative daily rate of -500 for the Nexon. Furthermore, the silent swallowing of unknown car returns was only revealed by carefully reading and executing the code. These critical business logic oversights prove that while static analysis successfully elevated our Pylint score from 4.94/10 to 10.00/10, automated functional testing and human code review remain indispensable.
